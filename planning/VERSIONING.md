# Project Versioning

This document defines the version identities used by planning, simulation,
fabrication, calibration, hardware, and experiments. A version label identifies
an artifact lineage; hashes and commits identify exact artifact contents.

## General Rules

- Use lowercase ASCII kebab-case labels.
- Use `-vN` for numbered revisions within one compatible lineage.
- Use short letter suffixes for physical prototypes when the letter is already
  marked on the part or assembly, such as `cad-proto-a`.
- Record `*-none` explicitly when a run does not use an artifact. Do not use an
  empty string, omit the field, or infer absence from the backend.
- Treat labels in an archived run as immutable. A changed artifact receives a
  new label or content hash.
- Do not write aliases such as `latest` into archived manifests.
- Record both the human-readable label and an exact revision where one exists.

## Version Identities

| Artifact | Label pattern | Exact identity | Initial examples |
| --- | --- | --- | --- |
| Source code | package version plus Git state | full Git commit, dirty flag, and source fingerprint when dirty | `0.1.0`, `0.1.0+code.41` |
| Native plant | `native-abstract-vN` | config content hash | `native-abstract-v0` |
| MuJoCo XML | `mujoco-<lineage>-vN` | XML SHA-256 | `mujoco-none`, `mujoco-abstract-v0` |
| Active-inference model | `agent-<lineage>-vN` | architecture/config hash and checkpoint hash | `agent-spatial-v0` |
| CAD | `cad-<lineage>-<revision>` | native-file and export hashes | `cad-none`, `cad-proto-a` |
| Calibration | `calib-<lineage>-vN` | manifest SHA-256 | `calib-none`, `calib-bench-v0` |
| Hardware build | `hardware-<lineage>-vN` | build manifest SHA-256 | `hardware-none`, `hardware-proto-v0` |
| Experiment config | `experiment-<study>-vN` | resolved-config SHA-256 | `experiment-dev-default-v0` |
| Checkpoint | `checkpoint-<lineage>-vN` | checkpoint SHA-256 | `checkpoint-none` |

The package version communicates a release lineage. The web viewer's
`0.1.0+code.N` value is a local, monotonically increasing source-change stamp
generated by `src/active_painter/version.py`. It helps a person detect a stale
server, but it is not globally unique and is not a reproducibility identifier.
The Git commit and dirty source fingerprint are the authoritative code identity
for a recorded run.

## Revision Rules

A label revision must change when its declared interface, geometry, parameters,
or semantics change in a way that can alter an experiment. Formatting-only
changes may retain the label when the exact content hash is still recorded.

- Increment the native or MuJoCo model revision for changed dynamics, geometry,
  frames, contacts, actuators, or default process parameters.
- Increment the agent model revision for changed latent variables,
  factorization, likelihoods, transition models, preferences, precision
  semantics, policy priors, or checkpoint compatibility.
- Increment CAD and hardware revisions for fabricated geometry, assembly, motor,
  encoder, driver, transmission, or wiring changes.
- Increment calibration revisions whenever measured offsets, scales, noise
  models, limits, or frame transforms change.
- Increment experiment config revisions when the intended experimental
  condition or protocol changes. Always hash the fully resolved configuration,
  including defaults.

Changing a filename alone does not create a new version. Changing an artifact
without changing either its label or recorded exact identity is prohibited.

## Run Recording

Every meaningful run receives a unique `run_id` and stores
`version-manifest.json` at the root of its output directory. "Meaningful" means
that the run may be used for debugging evidence, comparison, validation,
calibration, a figure, or a research claim.

The manifest records:

- schema version, run ID, and UTC creation time;
- package version, viewer build, full Git commit, dirty state, and source
  fingerprint;
- labels and content hashes for plant, backend model, agent model, CAD,
  calibration, hardware, experiment config, and checkpoint;
- the path and hash of the fully resolved runtime configuration;
- relative paths to the experiment manifest and failure log.

Paths inside a run manifest are relative to the run directory unless explicitly
marked as external. Hashes use lowercase hexadecimal SHA-256. Unknown required
identity is recorded as `unknown` and makes the run provisional; it must not be
used as confirmatory evidence until resolved.

The example at `planning/templates/version-manifest.example.json` defines the
initial field shape. T-003 may extend run metadata, but it must not silently
change the meaning of these version fields.

## Compatibility

Version equality does not imply checkpoint compatibility. A checkpoint may load
only when its stored architecture contract matches the current agent contract;
the checkpoint hash and load status are recorded separately.

Backends may intentionally use different plant labels. Comparisons must record
both and describe known approximations rather than giving unlike models a shared
label for convenience.
