# Provisional Sensor-Only MuJoCo Painting Loop

Date: 2026-08-06

Status: implemented and locally verified as a bounded integration baseline

Version: `provisional-sensor-simulation-v0`

## Owner Summary

The project can now make repeated marks in MuJoCo without giving the painting
policy exact live canvas, brush, or joint state. The runnable command is:

```bash
python -m pip install -e ".[dev,mujoco]"
python -m active_painter.web_server --plant-backend mujoco --enable-provisional-sensor-policy --stroke-tone-prior black
```

The black-tone prior is recommended for this first demonstration because the
camera cannot identify white paint thickness on a white ground. It is a
declared prior over mark tone, not a reward or procedural paint command.

The loop waits for camera and body posteriors, selects a painting policy by
expected free energy, predicts the action through an independent MuJoCo model,
executes the selected action, waits for a camera frame captured after action
completion, corrects its material belief, and plans again.

This is not yet a quality result. The profile is deliberately small and its
transition model starts without the old exact-state bootstrap. Its purpose is
to prove that the system boundary closes and repeats before investing in a
larger training corpus and longer-horizon planner.

## Demonstrated Loop

```text
independent camera exposure + MuJoCo sensor packet
    -> q(material) + q(body) + q(compact brush)
    -> active-inference policy posterior
    -> independent MuJoCo counterfactual forecast
    -> selected Cartesian-IK realization
    -> conventional execution and safety control
    -> physical paint deposition in the simulation process
    -> action-conditioned material/brush transition priors
    -> post-action camera capture and delivery
    -> camera posterior and separately logged VFE
    -> sensor-derived replay transition
    -> next policy posterior
```

A local diagnostic run completed two planned strokes and two causally matched
camera corrections in 9.709 wall-clock seconds. Material process coverage rose
to 0.07986, the material belief reached revision 5, replay contained two
camera-derived transitions, and the body-estimator time exactly matched the
MuJoCo sensor clock. These values are local integration observations, not
stable performance or painting-quality claims.

## What Does Not Read The Live Simulator

Painting-policy inference receives:

- registered global/foveal camera products through
  `camera-spatial-likelihood-v0`;
- `BodyBeliefSnapshot` from encoder, velocity, and provisional contact sensor
  packets;
- compact per-brush load/pigment beliefs;
- the selected action and motor-realization metadata; and
- learned-model parameters and declared preferences/precisions.

`ArmActiveInferenceDriver._planner_state` remains forbidden in sensor mode,
including when the provisional loop is enabled. Reset also refuses to inspect
the process object. The integration tests invoke this guard explicitly.

The live `ArmPainterSim` is not deep-copied into motor forecasts. The runtime
constructs a second MuJoCo plant from the canonical MJCF and a separate
material process. It uses different substrate-grain and brush RNG seeds. Each
forecast then initializes:

- joint position and velocity from the frozen body posterior;
- thickness, wetness, pigment mass, and tone from the frozen material
  posterior; and
- load and average pigment from the frozen compact brush posterior.

Forecast provenance explicitly says `no live ArmPainterSim state copied`.

## What May Still Use Exact Simulation State

The conventional execution and hard-safety layer below the selected painting
policy may use exact live pose, collision/contact, and process state. This is
the allowed engineering boundary in `AGENTS.md`: those mechanisms realize or
constrain a selected policy but may not choose the painting policy.

The simulated camera renderer necessarily reads the generative process to
create pixels, just as a physical camera reads light generated by the real
scene. The agent receives only the declared camera products. Exact material
coverage is retained in tests as a simulator-only evaluation label and never
enters the policy posterior.

## Explicit Smoke-Profile Approximations

To make the first integration loop interactive, the opt-in profile uses:

- 640 x 360 canvas-camera and 320 x 240 brush-camera acquisition renders,
  down from the MJCF-declared operational acquisition resolutions;
- eight sampled painting policies;
- one-step painting-policy temporal depth;
- one forecasted continuation candidate;
- one motor-forecast particle;
- Cartesian IK as the only motor-realization support; and
- no passage or passage-plan proposals.

Every policy still terminates in `stop`, immediate `stop` remains available,
terminal coverage remains conditional on `stop`, and all painting decisions
still use the declared EFE/posterior machinery. Restricting motor realization
to Cartesian IK fixes a below-policy realization for this smoke profile; it
does not select an actuator SKU or change the fixed RobStride assignment.

The independent forecast template currently uses:

- a fixed, freshly loaded MuJoCo model rather than a parameter posterior;
- independent fixed substrate grain rather than inferred grain;
- independent brush microstructure and a compact load/pigment belief rather
  than persistent held-paint/bristle history; and
- a zero-history compliance prior rather than an inferred deformation state.

These are declared model priors. They are not copied live values and they are
not hardware calibrated.

The reduced render sizes are a simulation-throughput approximation. The
camera process still applies acquisition noise and emits the same registered
global/foveal product contract, but this profile must not be described as an
operational sensor-equivalent camera realization.

## Learning State

The previous bootstrap consumes exact synthetic material states and remains
oracle-labelled. It is disabled automatically in the provisional sensor loop,
even if the ordinary web defaults request bootstrap transitions.

Each completed post-action camera correction adds exactly one transition:

```text
(previous camera posterior, executed action and realization,
 next camera-corrected posterior)
```

The driver attempts one bounded transition-model gradient step after each
accepted camera transition. Training remains inert until replay reaches the
declared batch size. This means the initial smoke run is an integration test,
not evidence that the transition ensemble has learned calibrated material
dynamics. First-mark consequences are nevertheless rescored through the
independent realized-execution forecast rather than through the live process.

## Initial Observation Gate

The runtime no longer plans immediately from the constructor's zero material
belief. In provisional mode it automatically polls the MuJoCo camera process
until at least one registered material likelihood factor has been assimilated.
Planning also requires a body posterior and the independently constructed
forecast template.

On canvas clear, full reset, or automatic episode restart, the camera process
and observation gate reset so a delayed frame from the previous canvas cannot
initialize the next painting.

## MuJoCo Clock Correction

Repeated execution exposed a separate plant integration defect. The
contact-release safety controller can reset the arm pose during an episode.
`MujocoJointPlant.reset_state` resets MuJoCo time, so the next sensor packet
previously appeared to move backward and `BodyStateEstimator` correctly
rejected it.

The controller now uses `reset_state_preserving_clock` for that in-episode
release only. Full episode resets retain their ordinary zero-time behavior.
The regression test verifies monotonic time, and the repeated-stroke test
verifies equality between the body posterior time and backend sensor time.

## Verification

The focused integration coverage verifies:

- default sensor mode still fails closed;
- the opt-in mode requires MuJoCo and sensor observations;
- live and forecast plants, data objects, canvases, and grain arrays are
  independent;
- the independent template uses different grain and brush seeds;
- exact planner-state construction remains forbidden;
- policy inference waits for initial camera and body posteriors;
- two active-inference-selected strokes deposit material;
- both strokes receive exactly one causally later camera correction and replay
  transition;
- forecast provenance denies live-process copying; and
- in-episode contact release cannot rewind the body sensor clock.

Current aggregate results are recorded in `docs/PROGRESS.md`.

## Next Steps

The shortest path from integration baseline to a useful model is:

1. collect an episode-split corpus of camera/body posterior transitions;
2. train and validate a sensor-compatible transition checkpoint;
3. add the local camera-derived brush-load likelihood;
4. expand candidate count, motor-realization support, particles, and temporal
   depth one dimension at a time; and
5. compare repeated sensor runs against the labelled oracle diagnostic without
   allowing oracle fields into features or online learning.

Longer-term embodiment work still includes a compliance likelihood,
substrate/model parameter posteriors, native-plant sensor adaptation, and
MuJoCo parameter uncertainty.
